01
Blockchain Fundamentals
proof of work · proof of stake · consensus · cryptography
Weeks 1–2 Month 1
Before touching a single line of code, you must understand what you are securing. Blockchains are adversarial environments where every transaction is public, irreversible, and executed by an untrusted virtual machine. Without understanding the underlying consensus and economic model, you cannot reason about attack surfaces. This step is your mental foundation — everything else builds on it.
📖Mastering Ethereum (Book) 📹Proof of Work vs Proof of Stake (Video) 📖The Eth2 Book 📄Ethereum Yellow Paper
Concepts You Must Understand
0/10
  • How Proof of Work achieves consensus and why it is energy-intensive
  • How Proof of Stake replaces computational work with economic stake and why it changes the attack model
  • What a 51% attack is and why it is economically costly in both PoW and PoS
  • The structure of an Ethereum block: header, transactions, receipts, state root
  • What the EVM is and how it differs from a normal computer (deterministic, gas-metered)
  • What Merkle trees and Merkle Patricia Tries are and how they enable trustless state verification
  • How public/private key cryptography works and how Ethereum addresses are derived from keys
  • The difference between EOAs (Externally Owned Accounts) and Contract Accounts
  • What finality means in blockchain and why transactions can be reverted before finality
  • Why blockchain immutability is a double-edged sword for smart contract security
Things You Must Be Able To Do
0/6
  • Explain to a non-technical person how Ethereum reaches agreement on the correct state without a central server
  • Read a raw transaction on Etherscan and identify the sender, receiver, value, gas price, and input data
  • Describe the flow of a transaction from broadcast to finality, step by step
  • Explain why a smart contract bug is catastrophic (no hotfix, no rollback, funds lost forever)
  • Sign a message with MetaMask and verify it, demonstrating you understand key-based identity
  • Calculate a Merkle root by hand for a small set of transactions and verify a Merkle proof

02
Solidity Fundamentals
syntax · types · storage · events · ABI · functions · modifiers
Weeks 3–4 Month 1
Solidity is the language you will audit. You don't need to be a developer — you need to be a reader and a skeptic. Every line of code you audit is a potential attack surface. Your job is to read contracts with the same precision a lawyer reads a legal document: every word matters, every omission matters, every assumption matters.
📄Solidity Official Docs 📹Smart Contract Programmer — Solidity 0.8 📄Secureum Solidity 101 📄Secureum Solidity 201
Concepts You Must Understand
0/12
  • All Solidity data types: uint, int, address, bool, bytes, string, arrays, mappings, structs, enums
  • The three storage locations: storage (persistent, expensive), memory (temporary, cheaper), calldata (read-only, cheapest)
  • Function visibility: public, private, internal, external — and the security implications of each
  • State mutability: pure, view, payable — and what each guarantees (or fails to guarantee)
  • How modifiers work and how they can create subtle bugs if chained or misused
  • What events and logs are, how they are stored, and why they are not a security mechanism
  • The ABI (Application Binary Interface): how Solidity functions are encoded for EVM calls
  • How inheritance, interfaces, and abstract contracts work and where they introduce hidden behavior
  • Constructor behavior and the difference between Solidity 0.7 and 0.8 (overflow protection, custom errors)
  • msg.sender, msg.value, block.timestamp, block.number — and why each is dangerous to rely on
  • The three ways to send ETH: transfer, send, call — and why only call is currently recommended
  • How try/catch works in Solidity and when it can fail silently
Things You Must Be Able To Do

03
Gas Optimizations
gas costs · storage layout · opcodes · EVM execution model
Week 5 Month 1
Understanding gas is not just about efficiency — it is about security. Gas limits can be weaponized (DoS via gas exhaustion), storage patterns affect reentrancy safety, and gas cost changes from EIPs can break assumptions contracts were built on. Every auditor must understand the economic layer of the EVM.
📄Juan: Advanced Gas Optimizations 📄Kaden: Gas Optimization Tips 📄Aggregated Tricks (pcaversaccio)
Concepts You Must Understand
0/9
  • Why storage operations (SSTORE/SLOAD) are the most expensive EVM operations and their exact gas costs (cold vs warm access)
  • How storage slot packing works and when it saves gas (multiple variables packed into one 32-byte slot)
  • The gas cost difference between memory expansion and calldata, and why calldata is preferred for function arguments
  • How a DoS-by-gas-limit attack works: loops over unbounded arrays that exceed the block gas limit
  • What EIP-2929 (access lists / cold vs warm storage) changed about gas costs and how it affects older contracts
  • Why short-circuiting in conditionals matters for gas (and how attackers can exploit predictable execution paths)
  • The gas refund mechanism (SSTORE to zero) and how it has changed over time (EIP-3529)
  • Why custom errors are cheaper than revert strings (gas implications for users)
  • Memory expansion costs: why large in-memory data structures can unexpectedly consume enormous amounts of gas
Things You Must Be Able To Do
0/5
  • Look at a function and estimate which operations will be the most gas-expensive before running it
  • Identify a loop-based DoS vulnerability in a contract and explain exactly how an attacker would trigger it
  • Reorganize a struct's fields to minimize storage slots used (apply variable packing correctly)
  • Explain why a push-based payment model (send ETH to array of recipients) is dangerous vs a pull-based model
  • Use Remix or Foundry to measure exact gas costs of two versions of the same function

04
Smart Contract Testing & Debugging
hardhat · foundry · unit tests · fuzzing · fork testing
Weeks 6–7 Month 1
An auditor who cannot write tests cannot prove a vulnerability. When you find a bug, you must write a Proof of Concept (PoC) — a test that demonstrates the exploit. If you can't write a PoC, the finding is just a theory. Foundry is the industry standard for auditing PoCs. Master it now.
📄Hardhat Docs 📄Foundry Book 📹Better Programming Hub 📹Code Eater (Hindi) 📹Tenderly
Concepts You Must Understand
0/8
  • The difference between unit tests, integration tests, and fork tests — and when to use each in auditing
  • What fuzzing is: automatically generating inputs to find edge cases, and why it finds bugs humans miss
  • What a fork test is: running tests against a mainnet fork with real state (Uniswap balances, real prices)
  • Foundry's cheat codes: vm.prank, vm.deal, vm.warp, vm.roll, vm.expectRevert, vm.expectEmit
  • How to use vm.store to directly write to a contract's storage slot (bypassing access controls in tests)
  • What a test invariant is and why invariant-based fuzzing is the most powerful automated testing technique
  • How to use Tenderly to simulate a transaction and trace the exact EVM execution step-by-step
  • What a Proof of Concept exploit test looks like and what sections it must contain (setup, attack, assertion)
Things You Must Be Able To Do
0/7
  • Set up a Foundry project from scratch, write a test file, and run it with forge test
  • Write a Foundry PoC that exploits a reentrancy vulnerability in a sample contract — the test should drain the contract's funds
  • Run a fork test against Ethereum mainnet using a real protocol (e.g., call Uniswap to get a real price)
  • Write a fuzz test in Foundry (function starting with testFuzz_) that tests a mathematical invariant
  • Use vm.prank to impersonate the contract owner and call a privileged function in a test
  • Trace a failing transaction on Tenderly and identify the exact line of code that reverted
  • Calculate test coverage with forge coverage and identify which branches are untested

07
Upgradeable Contracts
proxy patterns · EIP-897 · EIP-1822 · EIP-1967 · storage collisions · initializers
Weeks 10–11 Month 2
Upgradeable contracts are among the most complex and bug-prone patterns in all of smart contract development. Storage slot collisions, uninitialized proxies, and function selector clashes have caused real million-dollar exploits. If a project uses proxies, budget 30-40% more time for that audit.
📹Smart Contract Programmer — Upgradeable Contracts 📹Smart Contract Programmer — Risks of Upgradeable Contracts 📄EIP-897 (Proxy Standard) 📄EIP-1822 (UUPS) 📄EIP-1967 (Proxy Storage Slots) 📄EIP-2535 (Diamond)
Concepts You Must Understand
0/10
  • How delegatecall works at the EVM level: execution context is caller, but storage is callee's slots
  • Transparent Proxy (EIP-897): how admin/user function clash is prevented and the extra gas cost of admin checks
  • UUPS Proxy (EIP-1822): why upgrade logic lives in the implementation and the danger of accidentally bricking it
  • Storage layout collisions: why adding variables in the wrong position in an upgrade corrupts all existing storage
  • The uninitialized proxy attack: why initialize() must be called atomically on deployment
  • Function selector clashes between proxy admin functions and implementation functions
  • The Diamond pattern (EIP-2535): facets, the diamond cut, and why it was invented (bypassing contract size limits)
  • Why constructor logic cannot be used in upgradeable contracts (it only runs for the implementation, not the proxy)
  • Beacon proxies: how they allow updating many proxies in one transaction by changing the beacon's implementation pointer
  • Immutable variables and upgradeable contracts: why immutables in implementation contracts produce undefined behavior
Things You Must Be Able To Do
0/6
  • Given two versions of an implementation contract (V1 and V2), identify all storage layout incompatibilities
  • Write a Foundry test that demonstrates the uninitialized proxy attack (attacker calls initialize before the team does)
  • Use Slither's slither-check-upgradeability to detect upgrade safety issues in a proxy contract
  • Read a deployed proxy on Etherscan: find the implementation address from EIP-1967 storage slot 0x360894...
  • Explain the centralization risks of an upgradeable contract to a non-technical investor (the team can change anything)
  • Identify a function selector clash between a Transparent Proxy's admin functions and the implementation

Important Ethereum Improvement Proposals
EIP-150 · EIP-1559 · EIP-712 · EIP-2929 · EIP-4337 · ERC-4626 · ERC-2612
Week 25 Month 5
EIPs are the foundation on which every contract assumption is built. When gas costs changed with EIP-2929, protocols that relied on the old gas stipend broke. When EIP-1559 changed fee structures, systems assuming fixed priority fees were affected. Know the EIPs deeply, especially how they can invalidate previously-secure code.
📄EIP-150 (Gas Cost Changes) 📄EIP-1559 (Fee Market) 📄EIP-712 (Structured Data Signing) 📄EIP-2929 (Gas Cost for State Access) 📄EIP-4337 (Account Abstraction) 📄ERC-2612 (Permit)
Key EIPs You Must Understand In Depth
0/10
  • EIP-150: The 63/64 gas forwarding rule — why you can never send 100% of gas and how this affects reentrancy defenses
  • EIP-1559: base fee + priority fee, why base fee is burned, and how this affects contracts that used gasPrice for logic
  • EIP-712: structured data signing format, domain separators, and how to audit permit() implementations for vulnerabilities
  • EIP-2929: cold vs warm storage access pricing and how it affects protocols built before this EIP (2.3k gas vs 100 gas)
  • EIP-2930: access lists and how they allow pre-declaring storage slots to avoid cold access costs
  • EIP-3529: reduction of gas refunds and why this eliminated certain storage manipulation attacks
  • ERC-2612 (Permit): gasless approval via EIP-712 signatures and the front-running vulnerability in naive implementations
  • EIP-1167 (Minimal Proxy / Clone): how it works, the immutable bytecode, and why the implementation address is a security consideration
  • EIP-4337 (Account Abstraction): the UserOperation mempool, bundlers, paymasters, and the new attack surfaces they introduce
  • EIP-1271 (Contract Signatures): how smart contract wallets validate signatures and how isValidSignature() can be bypassed
Things You Must Be Able To Do
0/4
  • Audit an ERC-2612 permit() implementation and identify all edge cases (wrong domain separator, missing deadline check, replay)
  • Explain how EIP-150's 63/64 rule can be exploited to drain a contract that uses .call{gas:...} without checking return
  • Given an EIP-712 domain separator, manually compute the struct hash for a specific message and verify it matches the contract
  • Read a contract and identify which EIPs it implements — then check each implementation against the EIP specification for correctness

The Auditor's Arsenal
Slither · Mythril · Echidna · Manticore · Surya · Foundry · Tenderly
Week 26 Month 5
Tools are force multipliers, not replacements for skill. An auditor who relies only on tools will miss everything the tools miss. An auditor with no tools will waste time on what tools can automate. The goal is to know exactly what each tool can and cannot find, and to use them to free up your brain for the bugs that require human creativity.
🔧Slither (Static Analysis) 🔧Mythril (Symbolic Execution) 🔧Echidna (Fuzzer) 🔧Manticore (Symbolic Execution) 🔧Surya (Contract Visualization) 🔧Tenderly (Simulation) 🔧BlockSec ETH/BSC Tx Analysis
Concepts You Must Understand
0/7
  • What Slither is: a Python-based static analysis framework that detects vulnerability patterns without executing code — its strengths (speed, pattern matching) and weaknesses (no runtime context)
  • What symbolic execution is: how tools like Mythril/Manticore explore all possible execution paths mathematically (not just random inputs)
  • What Echidna is: a property-based fuzzer that takes user-defined invariants and tries to break them with random transactions
  • Why automated tools have false positives and false negatives and how to triage their output efficiently
  • What Surya does: generate call graphs, inheritance graphs, and function summaries to understand large codebases quickly
  • How to use Scribble to annotate a contract with formal specifications and run Mythril against the annotated version
  • The audit workflow: run Slither first (2 min) → review output → run Surya for visualizations → begin manual review → write Echidna invariants → write Foundry PoCs for findings
Things You Must Be Able To Do
0/7
  • Run Slither on any project, filter false positives, and identify 3 real findings from its output
  • Write Echidna invariants for a simple vault contract and run a fuzzing campaign that finds a bug
  • Use Surya to generate an inheritance graph and call graph for a large protocol (e.g., Compound) and use it to navigate the codebase
  • Use Tenderly's fork simulation to simulate a transaction against mainnet state without sending it on-chain
  • Set up a full audit environment: VS Code + Slither extension + Foundry + Echidna — in under 30 minutes on a fresh machine
  • Write a custom Slither detector for a specific pattern you frequently look for (e.g., missing zero-address checks)
  • Trace a complex exploit transaction using BlockSec's Phalcon Explorer and map each call to the relevant contract function

Mindset You Must Have
